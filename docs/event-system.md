# SQLite game catalogue

## Purpose and data boundary

SQLite is an authoring and runtime catalogue of **shared game data**: possible events, weekly-action definitions, typed game parameters, and parts for suggested streamer names. It holds player-facing option copy, chances and effects; starting values, run length, bankruptcy and balance constants; and the name vocabulary. It does **not** hold a player, run, save slot, chosen name, selected option, or encounter history. A player's identity, choices, rolls, and results are stored only in that player's browser save. The creator is considering roughly 200–400 distinct events for the first public release; the exact target remains open. The first documentation pass contains [20 draft examples](sample-events.md). Four working weekly actions are defined in [balance](balance.md); their numbers await playtests.

The domain engine receives immutable event and weekly-action definitions plus typed `GameParameters` through Application ports. `Infrastructure` loads and validates them from the same published SQLite catalogue version. The domain engine applies the content to its coded rules; it never queries SQLite or evaluates database-supplied scripts. The database supplies values and weighted outcome tables, while formulas and invariants remain in `Domain`. Name suggestions are a setup feature and do not consume the gameplay random stream.

## Proposed relational schema

| Table | Key fields | Purpose |
| --- | --- | --- |
| `CatalogVersion` | `VersionId`, `Status`, `PublishedUtc`, `ContentHash` | Distinguishes editable drafts from immutable published catalogues |
| `AdminAuditEntry` | `EntryId`, `OperatorId`, `OccurredUtc`, `Action`, `VersionId` | Records draft edits and publication by an authenticated operator; contains no player data |
| `GameParameters` | `VersionId`, typed numeric columns described below | Exactly one validated parameter row per catalogue version |
| `StreamerNamePart` | `(VersionId, Kind, PartId)`, `Text`, `Enabled` | Approved first or second name parts for suggestions; no player-chosen names |
| `WeeklyActionDefinition` | `(VersionId, ActionId)`, `GuaranteedCostPln`, `Enabled`, `SortOrder` | One player-selectable action per week; four working actions are in `balance.md` |
| `WeeklyActionText` | `(VersionId, ActionId, Locale)`, `Label`, `Preview` | Polish and English action copy |
| `WeeklyActionOutcome` | `(VersionId, ActionId, OutcomeId)`, `ChanceBps` | Weighted consequence of a weekly action |
| `WeeklyActionOutcomeText` | `(VersionId, ActionId, OutcomeId, Locale)`, `Result` | Localized outcome explanation |
| `WeeklyActionEffect` | `(VersionId, ActionId, OutcomeId, Ordinal)`, `Metric`, `Delta` | Additive viewer or drama effect |
| `WeeklyActionCashFlow` | `(VersionId, ActionId, OutcomeId, Ordinal)`, `Category`, `AmountPln` | Sponsor or donation income, or an expense; subscription remains the separate weekly formula |
| `EventDefinition` | `(VersionId, EventId)`, `OccurrenceChanceBps`, `EncounterCostPln`, `RepeatPolicy`, `CooldownWeeks`, `Enabled` | One possible event; `once` or repeatable after its cooldown, with an optional selected-event cost |
| `EventText` | `(VersionId, EventId, Locale)`, `Title`, `Prompt` | Polish and English situation copy |
| `EventCondition` | `(VersionId, EventId, Ordinal)`, `Field`, `Operator`, `Value` | Typed money, viewer, drama, week, and weekly-action conditions combined with AND in the MVP |
| `NarrativeFlagDefinition` | `(VersionId, FlagId)`, `Description` | Approved IDs for browser-local story-chain state; definitions only, never a player's flag values |
| `EventFollowUpGate` | `(VersionId, EventId, FlagId)`, `MinWeeksAfterSet`, `MaxWeeksAfterSet` | Requires a flag from a prior rolled result and limits the weeks in which this follow-up can be eligible |
| `TerminalReasonDefinition` | `(VersionId, ReasonCode)`, `Classification` | Approved special early ending reasons and their per-reason success/neutral/defeat classification; the three first-version reason codes and classifications are fixed below |
| `TerminalReasonText` | `(VersionId, ReasonCode, Locale)`, `Title`, `Recap` | Polish and English labels and recap copy for each special reason |
| `EventOption` | `(VersionId, EventId, OptionId)`, `GuaranteedCostPln`, `SortOrder` | Player choices; an optional cost becomes one expense entry before the roll |
| `EventOptionText` | `(VersionId, EventId, OptionId, Locale)`, `Label`, `Preview` | Localized choice and risk preview |
| `EventOutcome` | `(VersionId, EventId, OptionId, OutcomeId)`, `ChanceBps`, optional `TerminalReasonCode` | One possible result after choosing an option; an approved reason code may end the career early |
| `EventOutcomeText` | `(VersionId, EventId, OptionId, OutcomeId, Locale)`, `Result` | Localized result text |
| `EventEffect` | `(VersionId, EventId, OptionId, OutcomeId, Ordinal)`, `Metric`, `Delta` | Additive viewer or drama effect of that result |
| `EventCashFlow` | `(VersionId, EventId, OptionId, OutcomeId, Ordinal)`, `Category`, `AmountPln` | Sponsor or donation income, or an expense; amount is a non-negative magnitude with direction defined by category |
| `EventFlagEffect` | `(VersionId, EventId, OptionId, OutcomeId, Ordinal)`, `FlagId`, `Operation` | Sets or clears a browser-local narrative flag when this rolled result is applied |

`Bps` means basis points: `10,000 = 100%`, `500 = 5%`. The occurrence chance is evaluated when the event is eligible and not on cooldown. Outcome chances for each event response **and each weekly action** must sum to 10,000. The creator wants every player choice to have percentage-based consequences, so authoring should provide at least two meaningfully distinct outcomes per choice; a guaranteed cost is shown separately. Exact event odds belong in [event catalogue](event-catalogue.md); working action odds are in [balance](balance.md). The optional `TerminalReasonCode` is a controlled game-ending reason, not an arbitrary script or a fourth statistic. The first version permits the following codes and classifications:

| Reason code | Classification | Meaning |
| --- | --- | --- |
| `permanent_ban` | `defeat` | Permanent ban |
| `channel_closed` | `defeat` | Channel closure |
| `retired` | `neutral` | Retirement from streaming |

The selected outcome text and recap reason need equivalent Polish and English wording, with an honest pre-choice warning of any terminal chance. For every enabled text-bearing item, publication requires complete `pl-PL` and `en` rows. The same stable ID, odds, costs, conditions, and effects apply in both languages; changing copy creates a new catalogue version and updates its content hash. The published classification is pinned with the catalogue version; no first-version special reason has a `success` classification.

### Versioned game parameters

The first published `GameParameters` row uses these values. They are **initial content values**, not constants compiled into gameplay code. Confirmed game decisions remain the intended defaults; changing them later creates a new published version and affects new runs only.

| Typed column | Initial value | Domain use |
| --- | ---: | --- |
| `RunLengthWeeks` | 52 | Final week; no hard-coded week 52 check |
| `MaxEventsPerWeek` | 3 | Bound on sequential event selections after the single weekly action |
| `StartingMoneyPln` | 1,500 | Opening balance and base subtracted when calculating net profit |
| `StartingViewers` | 20 | Opening regular audience |
| `StartingDrama` | 50 | Opening public controversy level |
| `BankruptcyThresholdPln` | -1,000 | Inclusive defeat limit |
| `SubscriptionViewersPerPln` | 10 | Divisor in the proposed weekly subscription formula |
| `ScoreAudienceReferenceViewers` | 1,000 | Audience scale in the confirmed first final-score formula |
| `ScoreProfitReferencePln` | 5,000 | Net-profit scale in the confirmed first final-score formula |
| `ScorePointsPerComponent` | 500 | Equal point multiplier for audience and profit |
| `CalmDramaMax` | 33 | Last value in the calm band |
| `MiddleDramaMax` | 66 | Last value in the middle band; high begins above it |

Publish validation requires exactly one row per version; integer types; `RunLengthWeeks` in a proposed operational range of 1–260; a positive `MaxEventsPerWeek` with first published value **3**; non-negative starting viewers; starting drama within 0–100; a negative bankruptcy threshold below starting money; positive subscription divisor and score references; positive equal component points; and `0 <= CalmDramaMax < MiddleDramaMax < 100`. Reject missing, duplicate, unknown, or invalid fields, and reject event week conditions that are impossible under the configured run length. Use typed columns rather than an arbitrary key/value expression or executable formula. Changing an existing value creates a new draft and published catalogue version without changing gameplay code. Adding a new kind of parameter requires an EF migration, validation, and Domain support. Publishing freezes parameters, weekly actions, events, terminal reasons, and name parts together and includes all of them in `ContentHash`. A saved run pins its catalogue version and therefore its exact parameter row. The database stores no current player balance or defeat status.

The `StreamerNamePart` content contract and suggestion behavior are in [streamer name generation](streamer-name-generation.md). Publish at least two enabled first parts and two enabled second parts. The server selects one of each from the pinned setup catalogue version, concatenates them, and returns a suggestion. The chosen name stays in browser state, never in this table.

Allowed condition fields in the first release: `week`, `weeklyActionId`, `viewers`, `moneyPln`, `drama`, and `dramaBand`. Allowed operators: `equals`, `notEquals`, `lessThan`, `lessOrEqual`, `greaterThan`, and `greaterOrEqual` where appropriate. A band list can express eligibility for multiple drama ranges using the pinned parameter boundaries. The publish check rejects unsupported combinations. Conditions use the state after the one weekly action **and weekly subscription settlement**, before event effects. `EventEffect` targets are only viewers and drama; all changes to money use typed `EventCashFlow` entries. The event catalogue may author sponsor/donation income and expenses. The regular subscription payout is a coded weekly rule using the pinned divisor and cannot be emitted a second time by an event. The engine clamps viewers and drama according to [balance](balance.md). Never store C# type names, SQL fragments, reflection paths, or arbitrary formulas as executable event content.

`RepeatPolicy = once` excludes an event after its first selection in that career. `RepeatPolicy = cooldown` permits another selection only after its positive `CooldownWeeks` interval has elapsed. Selection, including one that immediately causes bankruptcy through an encounter cost, is the occurrence recorded in browser history. A follow-up uses the same repeat policy and normal `OccurrenceChanceBps` roll as any other event; a flag is only an eligibility gate, not a guaranteed appointment or an extra roll. An `EventFlagEffect` can set a flag with the current week or clear it after a response outcome. A follow-up's gate requires that flag from a prior week and a configured positive week-offset window. A flag can unlock alternative follow-ups; the selected follow-up's result clears or replaces it so the chain progresses or ends. Re-setting an already active flag does not reset its original week. Expire a flag deterministically once all of its published follow-up windows have closed. Store active flag IDs and their set weeks only in the browser save, pinned to the catalogue version. No flag changes when an event merely passes eligibility or loses collision selection.

## Dice sequence

1. Resolve the selected weekly action with one weighted outcome roll, including any sponsor/donation/expense entries. A guaranteed action cost may use debt and may temporarily reach or cross the pinned bankruptcy threshold. Settle subscription income once using the resulting viewers, the pinned `SubscriptionViewersPerPln`, and the versioned Domain formula. Reconcile the action and subscription entries **before** comparing the balance with the threshold; the rolled outcome and subscription settlement may rescue the run. If the final balance of that atomic step is at or below the limit, return a defeat state and recap for browser storage, then stop. Otherwise retain the resulting state and RNG state before evaluating events. No separate viewer milestone consumes an event slot.
2. For each event slot up to pinned `MaxEventsPerWeek`, expire ended chain flags and filter events using the **current** money, viewers, drama band, week, repeat policy, cooldown, and follow-up gate. Exclude events already selected in this week. For each newly eligible event not yet rolled in this week, sorted by stable `EventId`, consume one seeded random roll from 0 through 9,999 and record whether it passed `OccurrenceChanceBps`. Recheck earlier passing candidates against the current state; a candidate whose conditions no longer hold cannot be selected while ineligible. Each event receives at most one encounter roll per week, even if its eligibility changes later. If no passing candidate remains eligible, complete the week.
3. Choose one uniformly among the currently eligible passing candidates, with no preference for a flagged follow-up. Record its selection so it cannot appear again this week. Charge its `EncounterCostPln` **once** and record an expense entry; unselected candidates incur no cost. If the resulting balance is at or below the pinned threshold, return a bankruptcy recap with that event and cost, and do not offer responses. Otherwise persist the pending event, completed weekly-action roll and subscription entry, event count, rolled/passing/selected candidate IDs, paid encounter cost, and RNG state in the browser save before displaying choices.
4. For the chosen response, deduct and record its `GuaranteedCostPln` once even if that temporarily reaches or crosses the pinned bankruptcy limit; consume a seeded outcome roll and select one result by its `ChanceBps` interval. Apply its viewer/drama effects, cash-flow entries, any flag set/clear operation, and optional typed special ending as one atomic response step. Record the roll, outcome ID, deltas, and terminal reason. Check the reconciled money after the outcome. If it is at or below the limit, bankruptcy is the primary ending reason even when the same outcome carries a special reason. Otherwise, apply that special reason if present. A terminal result saves a recap and prevents further events.
5. If the run remains active, save this event's interim result and return to step 2 with the updated state. New eligible events can now receive their first roll of this week; earlier passing but unselected events remain candidates while eligible. A flag set by this week's result cannot unlock a follow-up until a later week. When the cap is reached or no passing eligible event remains, save one completed-week report containing the action and **all** selected events. Do not settle subscription income again.

An event's displayed `OccurrenceChanceBps` is its chance to pass its own eligible-week roll; the chance that it is finally shown can be lower if several events pass or the weekly cap is reached. This applies to chain follow-ups too, so a parent result never promises that a sequel will occur. Do not describe occurrence as an unconditional chance. The event's option preview should distinguish guaranteed effects from risky outcomes, including any result that ends the career.

## Catalogue versioning and updates

- Setup reads a published `VersionId` and its parameters. `StartRun` pins that version in the browser save, even if a new catalogue is published while setup is open. Every later week loads that exact version. Database row order must never affect seeded event selection.
- A published version is immutable. Editing creates a new draft version; existing runs continue using the old one. Keep old published versions while compatible browser saves may still exist.
- The first version includes an authenticated admin panel for drafting, editing, reviewing, previewing, and publishing weekly actions, events, game parameters, and name parts. The panel edits draft versions only; it displays validation failures before publication and commits a complete validated catalogue version in one SQLite transaction. A source-controlled seed/import tool may bootstrap initial content, but it is not the only publishing path. Record owner actions in `AdminAuditEntry`; the sole allowlisted GitHub account can perform all admin operations, including publication.
- The publish check verifies one valid `GameParameters` row including a positive multi-event cap (3 in the first published version), valid name parts in both groups, at least one enabled weekly action with stable IDs and valid weighted outcomes, unique stable event IDs, complete and reviewed Polish and English copy, at least two authored responses per event including a free fallback, at least two meaningfully distinct outcomes per choice, valid money/viewer/drama conditions and effects, sponsor/donation/expense entries, non-negative guaranteed/encounter/outcome cost magnitudes, effect limits, valid per-event repeat policies and cooldowns, occurrence chance from 0 to 10,000, and per-choice outcome chances summing to 10,000. The three approved terminal reason codes need a defined classification and complete Polish/English `TerminalReasonText` rows before publication; reject unknown codes or terminal results without clear risk preview. Validate that each flag ID is defined and produced by a published result, each follow-up window starts no earlier than the next week and ends within the run length, and each follow-up outcome clears or replaces its triggering flag. A missing translation blocks publication rather than silently displaying the wrong language.
- The publish check first runs `GameCatalogValidator` from `Domain`, the same check the weekly engine relies on, and then applies the publication rules above. The catalogue loader passes only enabled weekly actions, ordered by `SortOrder`. It passes each action's outcomes in a stable, persisted order, because outcome order decides which roll selects which outcome. `WeeklyActionOutcome` has no order column yet, so S2 adds one.
- Keep EF Core migrations separate from content updates. Schema migrations change table shape; draft/publish changes game content. The confirmed backup schedule creates encrypted, consistent copies daily and before each publication or migration, transfers them to the creator's second machine, and requires the pre-change copy to succeed before proceeding. Review SQLite table rebuilds and migration-lock recovery as described in [EF Core's provider limitations](https://learn.microsoft.com/en-us/ef/core/providers/sqlite/limitations).
- If a saved run requests a catalogue version that the server no longer has, return an explicit `catalog_version_unavailable` error and leave the browser save intact. Do not silently switch that run to a newer catalogue.

## Content management boundaries

The public player API can read and use published events, read the public setup parameters, and request a name suggestion. It cannot create, edit, preview drafts, or publish catalogue content. The admin panel and its draft/publish APIs live at `admin.polskistreamersymulator.pl`; all admin calls require a GitHub OAuth session authorized against the configured owner's stable GitHub user ID. No editor role is needed in the first version. Server-side authorization applies even when an endpoint is called directly, and the separate hostname does not replace it. Audit each edit and publication using the owner identity, timestamp, action, and target version, without copying player data into the audit trail. Keep draft content out of player responses. The SQLite file is mounted only into the private server workload; file paths and backups must not be copied into Blazor's public `wwwroot`.

## Example of one option with a reward roll

A `clip_spread` response could have a 70% result of `+60 viewers, +4 drama` and a 30% result of `+10 viewers, +1 drama`. A cautious response could have an 80% result of `+20 viewers, -1 drama` and a 20% result of no change. These are example odds for the data model, not approved balance values. The event itself is encountered only if eligible and its separate encounter roll passes. This distinction between **encounter chance** and **outcome chance** applies to every event.
